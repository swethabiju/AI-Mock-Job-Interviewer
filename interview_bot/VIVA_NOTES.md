# Viva notes - read this once before presenting (20 minutes)

## The 30-second explanation
"We fine-tuned Qwen2.5-1.5B with QLoRA to behave as a mock interviewer in three modes. A rule engine checks the candidate's answer
(STAR markers, technical key points, unit tests on submitted code) and passes the results to the model in a STATE line. The model
learned the interview protocol: one question per turn, probe what is missing, give hints in three levels without leaking code,
and finish with a valid scorecard. We measured this on held-out questions and messy phrasing against the prompted base model."

## Pipeline
1. `seeds.py` holds hand-written questions, key points and coding problems.
2. `gen_data.py` simulates candidates at different quality levels; `core.py` computes the correct interviewer action with rules.
3. Conversations are saved as chat JSONL; `01_train.ipynb` fine-tunes with LoRA on 4-bit weights, with loss **only on interviewer turns**.
4. `02_eval.ipynb` replays each held-out conversation up to every interviewer turn and scores the model's next reply with `metrics.py`.

## Likely questions and honest answers
**Why fine-tune instead of just prompting?** The base model also gets the full protocol in its prompt, so the evaluation is a fair
prompted-vs-fine-tuned comparison. Fine-tuning is meant to make the protocol reliable for a small model (format, one question,
no code leak, no false "pass"). Whether it did is exactly what the results table shows - report whatever it shows.

**Who decides the flow, the model or the code?** In the app the rule engine decides the action and tracks state, so the interview
never derails; the model writes the text. We show the model's own action next to the rule action, and `action_match` measures how
often they agree. This is a deliberate neuro-symbolic design, not a claim that the LLM does everything.

**Isn't the data fake?** It is synthetic by design: generated by script, so every label is correct by construction. Weakness:
it is repetitive and cleaner than real candidates. That is why the test set uses unseen questions and messy phrasing, and why we
added our own handwritten answers and report them separately.

**Why 1.5B and QLoRA?** It fits a free Colab T4 (4-bit weights, small LoRA adapters), and training takes under an hour.

**What does "loss only on assistant turns" mean?** Labels for the system prompt, STATE lines and candidate text are set to -100,
so the model is trained to produce interviewer replies, not to imitate candidates.

**How do you check technical answers?** Keyword/phrase markers per key point. It is crude: a correct answer in unusual words
can be missed, and a keyword dump can pass. State this as a limitation; do not defend it as semantic grading.

**How is coding checked?** Submitted code runs in a subprocess against hidden tests with a timeout. Hint level depends on the attempt number.
It runs untrusted code locally, so it is for Colab/local use only.

**What is `false_pass`?** The model said the code passed (FOLLOWUP) when tests had failed. It is the most important coding metric.
Note: an unparsable reply counts as "not a false pass", so read it together with `format_ok`.

**What is the base-model comparison really showing?** Partly format-following. Look past `format_ok` to `action_match`,
`content_ok`, `no_code_leak`, `no_false_pass` and scorecard error for the substantive differences.

**Scorecard error?** Gold overall = 5 x mean of the per-part scores, computed by code. The model must reproduce it from the STATE line;
`scorecard_abs_err` is the average difference.

**Why is this useful?** Students rehearse interviews with consistent, rubric-based feedback and safe code feedback; the design pattern
(checker + small tuned model) also lowers cost and hallucination risk.

**Limitations to volunteer:** synthetic data; keyword grading; small model; single-user demo app; 10 coding problems; no real hiring validity -
the scorecard is practice feedback only.
